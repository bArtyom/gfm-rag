- Table R@5 512 维反而**略高**于 1024（94.80 vs 94.75），不能说所有指标单调下降；但 Table R@10 略低且列召回下降，因此 Gate 仍未通过。

运行成本：全量加载与编码 GPU wall time 23.89 秒，总 wall 30.25 秒；1024 / 512 单独排序时间约 0.114 / 0.103 秒（整批问题），这些是本次单次小型全库穷举跑分的计时，**不是生产 ANN 索引或最终 SQL 端到端延迟**。

## 3. 结果隐含的主要瓶颈

### 3.1 表召回已接近饱和，而列召回仍明显不足

1024 维 Table R@10 = 99.91%，Column R@10 = 68.01%。因此下一轮应优先提升列检索的相关性和覆盖效率，而非继续做 Table 维度搜索。

**指标解释限制**：当前先在每个数据库内按类型挑 Top-10；对于表数不超过 10 的数据库，Table Recall@10 会在不需要语义排序的情况下天然达到 100%。应审计每库候选表数与 gold 表数，报告 *Top-K 的可达/饱和比例*，不能直接将 99.91% 解读为“语义表匹配已解决”。

### 3.2 2048-token “完整表列覆盖”对部分数据库不够敏感

聚合结果中，至少 6 个数据库在 1024 维的 Complete@2048 = 100%（debit_card_specializing、financial、toxicology、student_club、superhero、codebase_community），而这批库的 Column R@10 仍有明显差异。说明 2048-token 指标会受**Schema 大小 / 能否几乎全部装入**强烈影响。

本轮代码按分数递减遍历整库候选，只要节点文本长度放得进剩余预算就加入；不是“每次只拿 Top-10”。因此 79.66% 完整覆盖**不能**与 Column R@10 直接当作同一排序条件比较。

后续需要测 512、1024、2048 等多个**冻结的 Schema token 预算**、Gold 所需内容的 oracle-fit、实际返回项数量、Precision@Budget 与每库饱和率。不要仅增大预算刷覆盖率。

### 3.3 列级错误的原因目前仍未定位

实验报告只有汇总和匿名统计，没有公开的逐题分数与错误列，因此不能直接断言 Column Recall 损失来自“业务 JOIN 角色”或“Embedding 语义能力”，可能由短字段名、描述噪声、字段基数、候选数量、数据类型、值描述、同义词/缩写、预算文本长度等多种因素造成。

应先从本地私有逐题数据分析 **gold 列排名分布、已召回表下的列漏召回、列描述有/无、字段 token 长度、困难库结构**，再选择相似度改法；避免通过查看 Gold 反向为线上候选补答案。

### 3.4 论文迁移的技术边界

本次是 *Embedding-only* 检索，不是官方 G-reasoner 图模型复现；GFM checkpoint 的输入投影固定 1024，低维不能原封不动加载。**在 FK metadata / Join-Instance 标签未完成可追溯性审计之前，禁止宣称 Join/Role 改进。**

## 4. 数据和报告需补齐的缺口

1. 74 题 Column 标签不可评的明确分库/失败原因、对结论的选择性偏差。
2. P0 FK 闸门失败的**具体原因与可修复性**（复合 FK、缺少约束、Gold 非 FK join、元数据映射错误各多少），当前摘要只说没通过，不能代替详细记录。
3. 11 个数据库各自 Table/Column 候选量、gold 个数、问题数、节点 token 分布、2048-token 可装入全部 Schema 比例，辨别自然饱和。
4. 1024 基线 column gold rank 的分布和 512 vs 1024 的配对救回/损坏来源；不可用仅汇总数据推断逐题错因。
5. 旧全量实验节点文本 hash 与当前 type-first 文本 hash 不相同；缺少旧序列化规则，**不能把两个实验当成严格同输入复现**。下一轮固定并记录有序节点 ID 与文本、文本模板及序列化哈希。
6. 需记录真实模型加载/编码时间与检索排序时间分别随 d 变化；当前共用一次 1024 编码、截断重算，**不证明 512 维前向编码推理速度更快**。

## 5. 决策与下一步

**结论：STOP Dimension Sweep，转向 P1.5 数据/误差归因与预算审计（先离线、不新增 API）。**

- P1.5 先对已归档结果进行统计审计；若逐题/分数缓存可从本地重建，冻结候选排序并运行 1024 维的 gold-rank / saturation / budget-oracle 诊断，禁止凭空宣称已完成。
- P0-FK 并行只做元数据/标注修复性诊断。Role/Path 分支设置严格 Gate，未通过不做。
- 有条件的 P2a 仅在**同一候选文本、同数据、同预算**下对比 Cosine vs BM25 vs RRF，1024 维为主；512 作为资源对照，不是 P1 已通过的获胜者。
- 若这一步改善的是列排名而不是实际 Schema 覆盖，后续再评估下游固定生成/选择下的 Set EX；GNN、Jev 与 SQL 生成预算保持不变，不混合优化。
