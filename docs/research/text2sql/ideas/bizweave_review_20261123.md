# BizWeave Idea 评审：从业务文档到 Business–Schema 图

**评审日期：**2026-11-23
**输入：**[2026-11-23 讨论纪要](bizweave_discussion_minutes_20261123.md)
**评审性质：**探索阶段的单人评审与初步相关工作核对；不是完整系统综述，也不是新实验报告。

## 结论先行

**建议保留方向，收窄论文主张；目前不能声称“首次用业务语义图连接业务概念与数据库表列”。** 一个直接相关的 2026 年 Text-to-SQL 工作已经使用知识图谱表达业务概念，并显式维护知识模式到关系 Schema 的映射，用于 Schema Linking 和后续 SQL 编译。BizWeave 仍有可能形成差异，但候选差异必须落在：**如何仅从 Schema 与业务文档自动归纳带证据的映射，尤其是把相互依赖的多个业务概念联合对齐到一组物理列；以及这种结构在相同信息下是否优于普通双路检索。**

当前最合适的核心假设可以写成：

> 在 Schema 与业务文档、候选表列全集和检索预算相同的条件下，自动构建的、有来源证据的 Business–Schema 映射图，能否在低词面重合或跨字段依赖问题上，比分别检索 Schema 与文档更完整、准确地召回必要表列？

这把**联合对齐**作为候选核心机制，把图检索作为效用验证；SQL 生成、最终 JOIN 判定、弃答和完整本体构建按讨论纪要继续排除在当前主贡献之外。

## 1. 我对当前 Idea 的理解

- **输入：**数据库 Schema（表、列、键、已有描述）和业务文档。
- **离线产物：**业务概念、事件、指标、规则、组件、文档证据跨度、映射声明、物理表列等节点和关系；映射保留来源、核验状态、冲突或未决状态。
- **在线任务：**从问题定位业务/Schema 锚点，沿已核验关系召回相关表列，并返回可追溯的证据路径。
- **核心风险：**如果系统只是把 Schema 和文档都放进图，再用现成图检索器找节点，贡献容易被已有 KG-to-relational mapping、双路检索和 Schema 图检索覆盖。候选方法需要明确回答“哪些多字段关系是联合推断出来的、证据如何约束它、为何比独立字段匹配更好”。

建议把 `MappingAssertion` 视作有类型、有证据的对象，而不是裸边。例如它至少记录业务 Claim、一个或多个物理字段候选、来源文档跨度、关系/作用域、核验状态，以及“未知/冲突”。对于指标等跨字段含义，应允许一个业务定义映射到字段集合，而不是强制一对一。

## 2. 相关工作的重合与边界

| 工作 | 已覆盖的内容 | 对 BizWeave 的影响 |
|---|---|---|
| Nascimento et al., *A Text-to-SQL strategy based on large language models and knowledge graphs for real-world databases*（Data & Knowledge Engineering, 2026） | 定义业务知识 Schema / 图，以及到关系 Schema 的映射；其 DANKE 流程用知识图谱做 Schema Linking，再借映射合成关系数据库视图。论文说明知识 Schema 和映射由准备工具创建，示例还使用了业务文档给出的类/属性到表列映射、同义词和枚举值说明。 | **当前最接近的先行工作。**“建业务 KG、映射到表列、供 Text-to-SQL/Schema Linking 使用”不能作为单独新颖性。BizWeave 的潜在差异是自动从分散文档和 Schema 归纳映射、证据核验/冲突管理，以及多概念到字段集合的联合对齐。必须逐项对照原文和公开实现。 |
| BIRD-Ent / Spider-Ent 与 DRAG（Findings of EMNLP 2026） | DRAG 在 SQL 生成前分别检索表 Schema 和外部知识。公开卡片列出 BIRD-Ent 的问题、`gold_table_ids`、`gold_knowledge_ids` 等字段，并提供 Schema、知识文档和数据库资源。BIRD-Ent 有 1,534 道题、7 个 data-asset domain、1,412 篇约 150 万 token 的文档；构造中包含知识拆分和文档生成。 | 是适合做**强基线和候选数据集**的资源，不是天然的 Business Concept ↔ Column 金标。可以评测表和知识检索，但 BizWeave 的映射边仍需审阅/标注。Spider-Ent 没有外部知识检索任务，不适合单独验证“业务文档建图”的主假设。 |
| Graph-Link（ICML 2026）、SchemaGraphSQL（Findings of EACL 2026）、GRASP-SQL（SSRN 预印本） | 都把 Schema Linking 作为图或结构化子图检索问题；Graph-Link 以层级 Schema 图和 Steiner 子图优化保证结构连通，SchemaGraphSQL 基于 FK 图做路径搜索，GRASP-SQL 用异构 Schema 图、查询条件打分和连通子图抽取。 | 证明“图检索/连通子图”不是 BizWeave 的独有机制。它们应作为结构检索基线或可替换 Retriever；BizWeave 要证明的是业务文档到物理字段的**映射图本身**带来额外收益。GRASP-SQL 目前按 SSRN 预印本处理，证据权重低于正式发表论文。 |
| GeSI / EmSI（2026） | 从表头和样本值推断概念类型、属性、层级和类型间关系，生成概念 Schema。 | 自动概念 Schema 归纳已有先例；其重点不是把业务文档中的声明/指标依赖映射到关系表列，因此仍是近邻，而非完全相同任务。 |
| Schema-Free Text-to-SQL（arXiv:2610.33946，2026） | 从历史 SQL 日志中恢复隐式结构，并构建知识图用于 GraphRAG；论文报告业务概念与字段/表之间的使用关系可从日志恢复。 | 它走历史查询日志路线，BizWeave 走业务文档路线；但两者都触及“业务语义连接物理 Schema”。若日志后续加入 BizWeave，应先作为不同证据来源的扩展，不纳入当前主线。 |

目前发现的直接工作已经足以否定宽泛的“没人做过业务图映射 Schema”说法；但还不足以否定更窄的“文档驱动、证据可追溯的自动联合对齐”贡献。该窄主张仍需扩大文献检索，尤其检查 ontology/semantic-layer 到关系 Schema 的映射、自动 schema matching、企业指标语义层，以及从文档/日志恢复业务规则的工作。

## 3. 优点与主要风险

### 优点

1. **任务边界比之前清楚。**当前纪要将主任务定为 Schema Linking / Retrieval，而不是把 SQL 生成、JOIN 路径裁决、弃答和完整本体同时纳入。
2. **效果可以直接证伪。**最终要看必要表列是否被完整、正确召回，而不是图节点数量、JSON 合法性或生成文本看起来合理。
3. **证据路径有实际价值。**业务定义可以回到文档跨度，映射可以被审阅；这也支持发现冲突和拒绝无根据的自动补边。
4. **已有合适的比较框架。**纪要已经识别双路检索、Schema 图、文档增强图等对照，且强调相同输入、候选池和预算。

### 需要解决的问题

- **R1｜直接先行工作重合。**DANKE 已经把业务知识图谱、概念到表列映射和 Schema Linking 放在同一 Text-to-SQL 流程中。需把“人工维护映射”与“自动证据约束联合归纳映射”作为具体差异，并用原文/代码确认。
- **R2｜算法贡献仍是模块清单。**Claim 抽取、概念归一、候选匹配、证据验证、图检索分别都可能是常规模块。纪要中的加权目标式尚未说明联合结构怎样改变优化结果。建议把一个核心机制定为：相关 Claim/Metric Components 与一组字段映射共同求解，并明确关系兼容、证据支持和冲突如何进入候选生成或打分。
- **R3｜数据标签并不等于映射金标。**BIRD-Ent 公开字段包含表 ID 和知识文档 ID，足以支撑 DRAG 式检索对照；但这不自动给出“某段业务文字应映射到哪组表列”的人工真值。必须单独核验文档—字段映射，允许多解和不可判定样本。
- **R4｜要证明结构有增量价值。**若 BizWeave 看到更多文档或更多 token，它胜过 Schema-only 基线不能说明图有用。至少要同时对比：同信息的 DRAG 双路检索，以及将相同文档描述附到 Schema 节点的扁平增强图。
- **R5｜现有实验没有测试新主张。**BIRD 和 Spider 图 pilot 都只给模型 Schema/字段说明，没有业务文档；它们测到的是粗 Schema 图。先前在线需求抽取 smoke 的输出格式失败也不等同于离线文档建图失败。详见下节。
- **R6｜BIRD-Ent 的文档来源要谨慎解释。**公开说明称其包含知识拆分和文档生成，因而可以用来做受控基准与算法诊断，但论文结论不能直接外推为真实企业文档上的表现。

## 4. 既有实验能说明什么

| 已有工作 | 结果能支持的结论 | 不能支持的结论 |
|---|---|---|
| 2026-11-17 合成机制检查 | 手写业务映射与规则可以表达预设状态/事件/粒度差异。 | 不能证明模型能从真实文档抽取或正确映射业务语义。 |
| 2026-11-21 BIRD 零外键 pilot | 本地模型能从 Schema 生成结构合法的图草稿；typed graph 的 Recall@3/@5 提升，但 Recall@1/MRR 下降。 | 没有输入业务文档、语义金标或真实业务映射，不能作为 BizWeave 新主张的验证。 |
| 2026-11-22 Spider `bike_1` pilot | 再次显示 Schema-only 图能生成有效物理绑定；Recall@3 接近饱和，首位排序/MRR 低于 BM25。 | 不能说明文档到字段映射有效，也不能支持图检索优于强基线。 |
| 在线需求见证 smoke | 当前一条在线结构化需求输出路径未通过格式/覆盖门槛。 | 不检验离线 Business–Schema 图归纳，不能直接否定本次收敛后的 idea。 |

所以，当前全部 BizWeave 实验属于**相邻的可行性/工程先导证据**，没有一项直接检验 11 月 23 日版本的核心假设。主张中的第一项必要证据仍缺失：真实文档 Claim → 业务概念/组件 → 物理表列映射的准确性。

## 5. 最小验证路线

按信息增益排序，先做小样本可行性检查；它不是要求立即启动完整实验。

1. **先检查 BIRD-Ent 数据契约。**核对实际版本、许可、问题/文档 ID、`gold_table_ids`、`gold_knowledge_ids`、Schema 与文档内容；判断题目是否真的包含需要非平凡映射的例子。不要从 Gold SQL 生成图或构图提示。
2. **先人工审 1–5 条。**每条只标问题、必要表列、相关知识文档、证据跨度、映射是否唯一/多解/未知，以及是否存在跨字段依赖。若五条都只是文档直接重复列名，就不适合作为主假设的样本。
3. **做 Oracle Mapping 上界。**先用人工确认的映射测试图检索是否能改善完整表列召回。若正确映射也不能胜过相同信息的双路检索，就停止自动建图开发。
4. **上界有信号后再做 30–50 条探索标注。**按 domain 分组，优先低词面重合、跨字段依赖、指标组成和近似负例；报告可裁定率以及每条映射的证据支持质量。探索标注不作为最终测试集。
5. **只跑两个最有区分力的系统对照。**(a) DRAG/Schema+文档分别检索；(b) BizWeave 显式映射图。相同 Schema、文档、候选宇宙、模型输入预算和 Top-K。另加文档描述增强 Schema 图以区分“显式关系”与“多给文本”。
6. **指标聚焦 Schema Linking。**Table/Column Recall@K、完整必要表列召回、MRR/Recall@1、知识文档召回、映射 Precision/Recall、证据支持准确率、输出候选数与检索成本。SQL EX 留到检索收益成立后。

### 停止条件

- Oracle 映射不提升完整表列召回：停止“图结构带来检索收益”的主张。
- 同信息扁平增强/双路检索与 BizWeave 持平：将图降级为工程化证据组织，不再声称核心算法增益。
- 自动映射的证据支持精度不足，或人工可裁定样本过少：停止扩大模型实验，先改数据/标注任务。
- 只有低词面重合、跨字段依赖子集出现可信收益：收窄论文主张到该子集，不外推所有 Text-to-SQL。

## 7. 评审决定

**建议：继续开发，但先收敛算法和补足近邻工作核对；暂不宣称新颖性，也不把旧实验包装成主证据。** 方向上最值得保留的点不是“低外键库上建一张业务图”，而是“业务文档里分散的定义如何被自动转成有证据、可组合的多字段 Business–Schema 映射，并且比同信息基线更能找全字段”。
