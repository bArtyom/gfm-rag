# BizWeave：面向业务事件与约束的 Schema Retrieval

**状态：** pilot；**新颖性：** unknown。本文把原始提案收敛为一个可检验主张，不代表完整系统已经实现。

## 问题

同一批物理表可能支持不同的业务解释。仅知道表能否 JOIN，不足以判断问题问的是浏览还是购买、支付尝试还是支付完成、退款申请还是退款完成，也不足以确定计数粒度和事件时间。

## 核心假设

在候选物理连接都合法时，显式表示业务事件、状态/时间约束、粒度及其证据的映射，能比只按 Schema 词面相关性或最短连接路径排序，更准确地选出符合问题意图的可执行实现；必要映射证据不足时，系统应弃答或标记未决。

因果链：`事件/约束映射及证据 → 过滤不满足条件的实现 → 更高的正确实现选择率及安全弃答率`。

## 方法范围

用记录而非普通边表示一个业务映射：

`event + participant roles + tables + ordered joins + filters + grain + time basis + evidence refs + verification state`

在线问题解析成相同类型的意图字段，再按必需约束覆盖、证据状态和路径成本选择实现。候选不足或唯一性无法确认时保留未知状态。

## 这轮先检验什么

`bizweave_business_semantic_pilot_20261117_001` 只验证两个前置问题：

1. 在固定的合成零售 Schema 中，方法是否能区分四组最小对照（购买/浏览、支付完成/支付尝试、退款完成/退款申请、订单粒度/明细粒度），并对缺失或含糊证据弃答。
2. BIRD train/dev 中是否有足够多带明确状态、时间或粒度线索的 SQL 问题，可供后续人工核验和方法对比。

合成检查只能证明实现符合预设规则，不能作为真实数据上的有效性或泛化证据。BIRD 统计只估计候选标签供给，不评估业务语义准确率。BIRD-dev 是已使用的开发集。

## 论文主张边界

- 不把知识图谱、外键发现、Steiner 搜索、对比损失或把多源数据放进 KG 本身声称为新颖贡献。
- 候选贡献是“带来源与未决状态的可执行业务映射”如何约束查询条件下的关系/路径选择；它需要在真实业务数据上证明优于同信息的 Schema、词面和结构基线。
- 目前缺少真实企业文档/查询日志及经审核的业务事件、粒度和多金标路径标签。BIRD 的 Gold SQL 只能产生银标签候选，不能自动证明某个业务解释唯一正确。
- 在完成相关工作逐项核查及真实标签审阅前，新颖性保持 `unknown`；当前实验不能支持投稿级贡献或端到端 Text-to-SQL 收益。

## 下一步门槛

只有当后续数据能提供可审计的业务映射证据，并且在数据库分组的真实歧义样本上通过同候选、同信息对照，才进入训练或端到端 SQL 实验。若 BIRD 条件/粒度候选过少或无法人工判定，应把它降级为合成机制测试，另找有业务文档或可信查询日志的数据源。
